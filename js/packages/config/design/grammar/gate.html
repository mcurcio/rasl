The proposed shape

One grammar file; everything else is checked against it

The grammar file is the language. Tools check it, generate a test parser from it, and that parser writes the expected results every real parser must match.

design rule 1One file defines the language: tokens, grammar, value rules and tree-node names. Every check reads it.
design rule 2Every character lands in exactly one token, so printing the tokens gives back the file. Types are read after parsing, never by the lexer.
design rule 3Parse-tree kinds are language concepts (directive, block, list, slice), not however the grammar happens to be split into rules.

These are design choices, not requirements, and can be revised.

The grammar · syntax

Directives, blocks, lists and slices

This is the syntax half of config.ebnf, in W3C EBNF. Spaces and comments are written out explicitly, so the grammar fixes exactly where they may go.

Document     ::= Bom? Statements EOF                  /* cst: document */
Statements   ::= Filler* ( Directive Filler* )* LastDirective?
Filler       ::= Space | Comment | Newline | ';'
Directive    ::= Header ( Separator | Block )          /* cst: directive */
LastDirective::= Header                                /* before } or end of file */
Header       ::= Word Rest
Rest         ::= ( Gap ( Value Rest )? )?
Gap          ::= ( Space | Comment )+
Separator    ::= ';' | Newline
Block        ::= '{' Statements '}'                    /* cst: block */
Value        ::= Word | String | SlicedWord | List
SlicedWord   ::= Word '[' Bounds ']'                   /* cst: slice, touching */
Bounds       ::= Word ':' Word? | ':' Word
List         ::= '[' ListGap? Items? ']'               /* cst: list */
Items        ::= Value ListGap? ( ',' ListGap? Items? )?
ListGap      ::= ( Space | Comment | Newline )+

A directive ends at ; or a newline. { must be on the header's line. Lists take commas (a trailing comma is allowed) and may span lines.

QUESTION 2 OF 3

Must values be separated by a space, everywhere in the language?

Today "a""b", a"b", [a][b] and a[0:3]b are read as separate values without a word, and x a [0:3] reads the same as x a[0:3].

QUESTION 1 OF 3

How are comments written, and may a word that starts with a digit contain :?

Every repo .conf uses #, but the old rule says // and /* */ only, and today all three work. Allowing all three clashes with / inside words. Draft 2 also bars : from words that start with a digit, so that [144:152] reads as a slice. That breaks server 127.0.0.1:3000; (a test fixture in parser.test.ts), MAC addresses like 00:11:22:33:44:55, and 10:30.

The rest of the grammar is recommended as shown:
  • Numbers are JSON numbers read from a whole word, so JS and Python agree exactly. 1_000, 0x10 and .5 stay words.
  • An invalid escape like \q becomes an error (today it is a warning), so \u can be added later without changing what any file means.
  • A lone carriage return is an error, and CRLF is one newline. A byte-order mark is allowed only at the start.
  • Outside strings and comments only ASCII is allowed, as today. In strings and comments, control characters are excluded, tab aside.
  • Error positions count characters (code points), not UTF-16 units or bytes. The cost: the TS parser converts, because JS strings index in UTF-16.
  • x {} y on one line is valid: a block needs no separator after it.
Soundness

What is proven, what is tested, what is not run yet

R2(a) is proven by two tools. R2(b) can only be shown by testing, since there is no tool that proves a hand-written parser equals a grammar, and the shipping TS parser hasn't been rebuilt yet.

PROVEN(a) one parse per inputREx: "grammar is LALR(1)". Bison: 0 conflicts. Both run on the real file and fail on 5 deliberately broken grammars.
PROVENtokens never overlapREx finds no string two token kinds both match. Planted overlaps are caught.
TESTED(b) test parser = grammar14,830 generated inputs: REx's and Bison's parsers agree on every verdict and error position. 0 round-trip failures. All 5 repo files are valid.
NOT RUN(b) TS parser = grammarThe TS parser gets judged by the same cases once it is rebuilt. Python likewise.

Gaps the review found, fixed in the first build step

  • The test parser treats a NUL character as the end of the file, so it accepts some input the grammar rejects. It must follow the grammar's character rules, and the test cases must include control characters, emoji and NUL.
  • Both checks rely on REx's lexer, so the lexer needs an independent check. REx also has a lexer bug, which I reproduced: I'll pin a released REx and report the bug upstream.
  • The rules for which error comes first, and for recovery, live in test code today. They move into the spec, beside the grammar.

The three layers

Grammar, then parser output, then sugar

// Layer 1: the spec as data. One conformance case, written by the test parser.
interface ICorpusCase {
  readonly input: string;                    // document text
  readonly tokens: readonly INormToken[];    // every character in exactly one token
  readonly cst: INormNode | null;            // null when the input is invalid
  readonly first: INormDiagnostic | null;    // earliest error, null when valid
}
// Layer 2: the TS parser (core, no I/O). Existing names kept.
export function parseDocument(source: string): IParseResult;
export function valueOf(doc: ICstDocument, value: ValueRef): IValue;  // the one decider

export interface IToken {
  readonly type: TokenType;     // Number token removed
  readonly text: string;        // the raw text; no decoded `value` field
  readonly span: ISourceSpan;
}

export type CstKind =
  | "document"
  | "directive"
  | "block"
  | "list"
  | "slice"
  | "error";                    // a recovered region (D3)
// Layer 3: TS sugar. Reads IValue and never re-parses text.
export type IValue =
  | { readonly kind: "word";    readonly text: string }
  | { readonly kind: "number";  readonly text: string; readonly number: number }
  | { readonly kind: "boolean"; readonly boolean: boolean }
  | { readonly kind: "string";  readonly decoded: string }
  | { readonly kind: "slice";   readonly target: string;
                                readonly start: number | null;   // null in [:m]
                                readonly end: number | null }    // null in [n:]
  | { readonly kind: "list";    readonly items: readonly IValue[] };
  // each variant also carries span: ISourceSpan

export interface IAstDirective {
  readonly name: string;
  readonly values: readonly IValue[];   // replaces args / argValues
  readonly body: IAstDirectiveList | null;
}
// DirectiveDelegator (rasl-stq) and declarative definitions (rasl-xlo) take IValue.

Costs and deferrals

What this gives up

  • Costs: an external C++ tool with one maintainer in CI; about 440 lines of scripts; breaking changes in tokens, tree and offsets, with no shims; recovery test cases reviewed by hand.
  • Not proven: R2(b) for the shipping parser rests on testing, not proof (shape A).
  • Deferred: \u escapes (rasl-m8w.2); the porting guide (rasl-ss7); fuzzing (rasl-a82).
  • Not planned: units like 200ms in the grammar (a consumer reads them); block comments, under Q1 A or B.
